# AI 增强功能大致计划（暂缓，待核心稳定后启动）

> **状态：** 仅规划，未实现。等跨设备同步、工作区同步等核心功能稳定后再评估启动。

## 目标

用 AI 减少标签管理的**手动负担**（整理、查找、清理），不追求噱头。所有 AI 功能必须 opt-in、最小数据、明确告知，避免把敏感标签数据无谓上传。

## 是否需要 AI

Tab 管理器的核心价值（整理、查找、清理）靠好的规则和 UX 就能实现，**AI 是增强而非必需**。值得挑 1-2 个高价值点探索，不建议全面铺开。

## 功能候选（按 价值 × 可行性 排序）

| 功能 | 价值 | 可行性 | 说明 |
|------|------|--------|------|
| 智能分组建议 | 高 | 中 | 标签不匹配规则时，AI 按 标题+URL 建议归类（"调研/购物/工作"），用户确认后可转为规则留存。直击"整理繁琐"痛点 |
| 清理助手 | 中 | 高 | 识别长期未用、重复、低价值标签，给关闭建议 + 理由。帮 declutter |
| 语义搜索 | 中 | 中 | "上周看的 Rust async 文章"按语义匹配，而非关键词。重度用户有用，需嵌入索引 |
| 标签摘要 | 中低 | 中 | 看板里用一句话摘要代替标题，帮识别。但取页面内容较重、隐私压力大 |
| 工作区自动命名 | 低 | 易 | 保存工作区时根据标签内容建议名字。小便利 |

## 关键约束（动手前必须先定）

1. **隐私**：标签数据敏感（银行、邮件、工作文档）。必须 opt-in；只发标题 + URL，不发页面正文；UI 明确告知"以下数据将发送给 AI"。
2. **LLM 接入**：扩展不能内置 API key（会泄露）。方案二选一：
   - Supabase Edge Function 代理调用 Claude（开发者 key，有成本可控）
   - 用户自带 key（设置页填入，存 `chrome.storage.local`）
3. **成本**：逐标签分类很贵。必须批量调用 + 缓存分类结果（同域名下次复用，避免重复请求）。

## 推荐起点：智能分组建议

直接解决核心痛点，数据量小（标题 + URL），opt-in 即可，且能融入现有"分组规则"体系（AI 建议可一键转为规则留存，形成闭环）。

### 大致数据流

1. 用户在看板选中若干未分组 / 待整理的标签，点"AI 建议分组"（新按钮，仅 opt-in 后可见）。
2. 扩展把这批标签的 `{ title, url }`（剥离其他）发给 Supabase Edge Function。
3. Edge Function 调用 Claude（系统提示：把标签按主题聚类，输出分组名 + 各组包含的 boardKey 候选，返回 JSON）。
4. 扩展拿到建议，以**预览**形式展示（分组名 + 标签列表），用户可：
   - 确认 -> 应用分组（走现有 move-board-tab 逻辑）
   - 把建议转为规则（域名/关键词 -> 分组，写回 groupRules）
   - 取消
5. 同域名的分类结果缓存到 `chrome.storage.local`（带 TTL），下次同域名标签直接复用，不打 AI。

### 涉及改动（预估）

- `supabase/functions/suggest-groups/`：Edge Function，接收标签列表，调 Claude，返回 JSON。
- `src/shared.ts`：建议结果的类型 + 校验。
- `src/background.ts`：`suggest-groups` 消息 handler（转发到 Edge Function）。
- `src/board.ts`：opt-in 开关 + "AI 建议分组"按钮 + 建议预览弹窗。
- `src/options.html/ts`：AI opt-in 开关 + key/隐私说明。
- 新设置项 `aiGroupingEnabled`（默认 false）。

## 暂缓理由

当前跨设备同步（设备标签快照）、工作区云同步刚落地/在收尾，核心体验还在打磨。现在引入 AI 会分散精力，且隐私/成本模型需单独设计。建议核心稳定后再启动，先把上面的"智能分组建议"做成可验证原型。
